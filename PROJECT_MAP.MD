# Vikings Strategy Game - Project Map

## Overview
Turn-based strategy game in Godot 4.3 with procedural map, resources, recruitment, movement, and battles for up to 6 players. Architecture emphasizes separation of concerns and SRP.
- Localization: gameplay UI/runtime messages in scripts use `tr(...)`; enum display text should use display/localized helper APIs (canonical enum string methods remain for data/serialization).
- AI behavior reference: `AI_BEHAVIOUR.md` documents current AI turn economy flow, target scoring, and movement/battle decision logic.
- Castle threat reference: `CASTLE_THREAT_LOGIC.md` documents runtime castle-threat detection/classification and per-army threat response branches.
- Player guide reference: `GAME_GUIDE.md` provides player-facing explanations of economy, recruitment, battles, sieges, and core strategy.
- Rendering/runtime defaults: project settings enforce VSync (`window/vsync/vsync_mode=enabled`) for frame pacing; 2D pixel snap is disabled to avoid zoom-time jitter and stepped camera/cloud motion, while clouds use per-sprite `Linear with Mipmaps` filtering.

Start Flow
- Main menu sets `SceneTree` meta `start_payload` and loads `main.tscn`:
  - Scenario: `{ type: "scenario", scenario_path: res://scenarios/<name>.json }`
- Custom map: `{ type: "map", map_file: res://mapdata/<file>.json, map_size: <tiny|small|medium|large|huge>, player_settings: [...], victory_condition: <""|conquer|dominate> }`.
- Saved game: `{ type: "save", save_path: user://<save_name>.json }` (path chosen from available save files; default save path remains `user://savegame.json`).
- `GameManager._ready()` reads `start_payload`:
  - Scenario: sets `game_mode = "scenario"`, assigns `scenario_path` (pre-load applies scenario map file) and loads scenario-defined `victory_conditions` (missing/empty means no automatic victory).
  - Custom map: sets `game_mode = "custom"`, assigns `MapGenerator.data_file_path`, applies compatibility `map_size` via `_map_set_size_from_string`, applies player_settings if present, reads `victory_condition`, then `generate_map()`.
  - For scenario/custom starts, reads `difficulty` and stores it as `GameManager.game_difficulty` (single runtime source for difficulty-dependent systems).
  - Save: loads the path from payload (`save_path`), regenerates map from saved source (`map_file` + compatibility `map_size`), initializes managers without castle-placement bootstrap, then applies full runtime state (regions/ownership/castles/armies/player/game turn state).
  - Payload is cleared after consumption.
- Custom map start shows `MessageModal` prompt "Click a region to choose your starting location" during castle placement.

## Core Managers & Flow

### game_manager.gd (GameManager)
- Purpose: High-level orchestration (castle placement, turns, resource ticks, AI start, battle finalization).
- Key: `initialize_managers()`, `next_turn()`, `_process_round_start_actions()`, `_process_player_turn_start()`, `handle_castle_placement()`, `finalize_battle_result(...)`.
- Integrates: RegionManager, ArmyManager, BattleManager, VisualManager, UIManager, PlayerManagerNode, TurnController, AIDebugVisualizer, CastlePlacementScorer.
- Victory system: stores normalized `victory_conditions`; checks at turn start and after movement/battle; supports `conquer` (others have no castles and no armies), `conquer_after_events` (same conquer check, but only after all runtime scenario events are marked triggered), `dominate` (>=70% conquerable regions: non-ocean, non-mountain), scenario-targeted `own_region`, `survive_turns`, and `economy` (player owns target region, reaches required region level and castle level there, and has hired required count of a specific unit type). Empty list means no automatic win trigger.
- Economy tracking: `record_hired_units()` tracks per-player hired totals by unit type (shared across human and AI recruitment flows), used by `economy` victory and persisted in saves as `player_hired_units`.
- Scenario rule: `scenario_trade_disabled` is loaded from scenario JSON `trade_disabled` and exposed via `is_trade_disabled_for_current_game()` for TradeModal rendering.
- Win/fail flow: outcome resolution is victory-first (`Player X Won` takes priority if met). Human elimination is evaluated after victory checks: eliminated humans are marked `OFF` (removed from turn order), show `Player X lost`, and play continues while at least one human remains. If no humans remain, Continue exits to main menu; for campaign scenarios it routes to `main_menu_target = "campaign_list"`. Single-human terminal defeat uses `You failed`. For regular victory popups (`Player X Won`), Continue now returns to `main_menu.tscn` (campaign Player 1 still uses the dedicated outro path to campaign list).
- Scenario events: on scenario init, each event pre-rolls a single `turn` from `[turn_start, turn_end]` and shuffles candidate region IDs once. At matching player turn start (before normal turn-start economy/actions), AI/off-player events keep legacy auto-spawn behavior (first non-full valid region from shuffled pool, then immediate battle check). Human-owned events now use manual SpawnEvent placement: event message (shown in `EventMessageModal`) -> armies-only InfoModal lock with spawned army selected -> highlighted allowed target regions with custom arrows from adjacent ocean sources -> right-click target to place -> immediate battle check -> spawned army movement points forced to 0 after placement resolution. Human event messages focus the camera on the event’s first configured region ID; AI events focus on the actual auto-selected spawn region.
- Scenario intro: `IntroMessageModal` is shown before the first turn starts using scenario `intro_message` plus `objectives` (joined with one blank line when both exist, each resolved via `tr(...)`). Optional scenario JSON key `skip_intro` (default `false`) skips this auto-show at scenario start. Campaign victory outro text uses key `mission-<mission_number>_outro`. `objectives` is persisted in scenario JSON and shown on main-menu scenario panel. Editor saves intro/description/objectives fields as translation keys.
- Debug: `debug_disable_battle_modal` — when true, AI battles run instantly in background (no modal, no delays).
- `debug_mode`: when false, AI turns hide the PlayerStatus panel, IconsModal (trade/map icons), and TurnModal end-turn button (keeps AI HUD minimal).
- Debug language shortcut: when `debug_mode` is true, pressing `Z` cycles locales in-game (`en` → `de` → `pl` → `br`), refreshes `TurnModal` text immediately, and saves the selected locale to settings.
- Camera: Sets initial zoom from map profile (`region_count`-anchored interpolation preserving known values: Small=1.0, Medium=1.5, Large=2.0) and clamps zoom-out to 0.5.
- AI memory: Records observed enemy army power for computer players after each battle (5-round decay window via `GameParameters.ENEMY_ARMY_MEMORY_ROUNDS`).
- AI memory: Records observed enemy garrison power when computer armies attack a region (shared 5-round decay window).
- Enemy intel snapshots: `_record_both_sides_power_snapshot()` captures defender forces for the attacker and attacker forces for the defender on early withdrawals; `_record_battle_power_after_resolution()` refreshes both sides' sightings after losses/retreats so AI knowledge stays current.
- Siege sims: `simulate_siege_battle(attacker, region)` runs AI-style siege prep on cloned wall/gate states (no resource spend/state changes) and feeds `BattleSimulator` so AI can judge castle fights during planning; it uses known defender intel (tracked armies/garrison) for attacker-side scouting.
- Castle threat sims: `simulate_castle_threat_battle(attacking_armies, region)` merges multiple attackers from one nearby region into a single simulated composition and runs against full defenders (all defending armies + garrison + recruits) for castle-threat classification.
- AI: Uses `TurnController.start_turn()` for computer players; castle placement uses `CastlePlacementScorer` with randomness.
- AI turn handoff: after an AI turn completes, `next_turn()` is queued via `call_deferred` (not immediate recursion), and turn advancement always waits for pending battles plus battle finalization (`_await_pending_battles()` + `BattleManager.await_finalize_complete()`) before switching players.
- AI turn safety: TurnController now skips invalid/freed army handles before per-army processing and guards decision-cycle continuation checks against freed references, preventing async turn-loop crashes when an army is removed mid-cycle.
- AI battle edge safety: threat-attack turn locks now use pre-captured army instance IDs across awaited battle movement, and GameManager AI battle-log queue/token helpers ignore freed army references, preventing `get_instance_id()` calls on destroyed armies.
- Turn-advance guard: `next_turn()` now uses an internal in-progress lock to prevent overlapping/re-entrant turn transitions (e.g. duplicate end-turn triggers) from skipping players.
- AI Step Gate: `ai_step_requires_shift` forwards to `DebugStepGate` — when true, AI waits for Shift to advance; false lets AI run automatically.
- AI Logging: Owns `AILogManager`; `ensure_ai_log_started()` names the log `<scenario>_<timestamp>.txt` the first time any AI player takes a turn so all later TurnController events can append to the same file inside the root `logs/` directory; logging is disabled when demo mode is enabled.
- Round start caches the average power of all armies each round so AI economy can compare castle garrisons against the global baseline.
- AI Siege: `_execute_ai_siege_preparation()` rolls trebuchets between `(castle_level - 1 - destroyed_walls)` and intact wall sections, reduces by attacker/defender power advantage above 3:1 (defender power = garrison + recruits + owned armies), then clamps by siege points/wood/caps; rams spend random remaining points up to intact gates (respecting caps/wood), ladders take the leftover points. AI fires trebs once before battle (`trebuchet_bombard` payload, no double wall damage) and ships `siege_view_state` with ram HP.
- Castle assault gating: AI castle attacks now run a no-side-effect siege simulation before spending resources; only predicted victories proceed. Simulation logs include siege purchases, assault/defense values, and pre/post compositions.
- Battle Log Queue: `finalize_battle_result()` snapshots attacker/defender forces before and after `_battle_manager._apply_battle_losses()`, converts the result into readable lines (`Battle started`, attacker/defender power/composition, `Battle Result`, post-battle status) and queues them per attacking army via `consume_ai_battle_log_for_army()` so TurnController can append them immediately after its movement logs.
- Initial castle placement (human or AI) now spawns a Keep immediately rather than an Outpost, so every starting stronghold begins at level 2 with the associated recruitment caps and visuals.
- Debug overlay: `show_region_center_markers` draws a small red square at each land region center by calling `MapGenerator.set_center_markers_enabled()` after startup and whenever the map regenerates.
- AI pre-battle withdrawal: before siege prep, AI attackers back out if attacker power ≤ defender power after defense bonus; after siege prep (or for open-field fights) AI withdraws immediately when the standard withdrawal power threshold is met (no roll, no casualties).
- Starting army composition lookup now uses `game_difficulty`: human starts are difficulty-dependent (Easy > Normal > Hard), while AI starts stay unchanged.
- Starting player resources now use `game_difficulty` presets for active players at initialization (Easy: 150/100/30/20/20, Normal: 100/50/20/10/10, Hard: 80/30/10/0/0 for Gold/Food/Wood/Iron/Stone).
- Target scoring: known enemy power (tracked armies + tracked garrison) is checked against the same withdrawal thresholds; regions with stronger known enemies are skipped during frontier target selection.
- Target scoring: known enemy power is adjusted by castle defense and a conservative assault multiplier; castles require a projected ratio > 1.5 to be considered, while open-field targets require > 1.0; pursuit bonuses apply the same castle adjustments.
- Battle intel snapshots now record attacker army intel for the defending player regardless of defender control type, and defender intel is also captured at battle start so human defenders consistently keep enemy army intel for InfoModal.
- Map Editor: `enable_map_editor` flag — when true, skips castle placement/turns, initializes MapEditor, shows empty editor panel (25% left).
 - Modes:
   - Custom: current behavior (castle placement → gameplay).
- Scenario: set `game_mode="scenario"` and `scenario_path` before start; map is regenerated from scenario `map_file`, managers init, then `ScenarioManager.apply_to_runtime(..., game_difficulty)` is called. Skips castle placement and starts the first turn immediately.
- Demo-mode start guard: when `GameParameters.DEMO_MODE_ENABLED` is true, `GameManager` sanitizes `start_payload` targets so only whitelisted scenario files and custom-map files can be launched (`DEMO_ALLOWED_SCENARIO_FILES`, `DEMO_ALLOWED_CUSTOM_MAP_FILES`).
- Scenario player settings: when scenario JSON includes `player_settings`, `GameManager` applies them before runtime scenario data, reinitializes `PlayerManagerNode` with those types, and then resolves first turn from active players only.
- Scenario resources: `ScenarioManager.apply_to_runtime()` pushes `player_resources` into `PlayerManagerNode.set_player_resources()` before the first turn.
- Scenario events: `_initialize_scenario_events_from_data(...)` now resolves optional `difficulty_overrides.<difficulty>.event_compositions` before event turn/region randomization and spawn.
- Scenario event auto-spawn flow now spawns the event army before camera focus, then when immediate battle is required it waits a fixed real-time `1.0s` after camera focus before triggering battle so players can see where the spawn occurred.
- AI target-score overlay visibility is now strictly gated by `GameManager.debug_mode`; AI turns no longer auto-show `_ai_debug_visualizer` when debug mode is disabled.
- First turn: `_process_player_turn_start()` skips economy/food for each player the first time it runs so HUD deltas stay `+0`; actual income/upkeep begins when that player starts turn two.
- First turn startup now explicitly calls `SoundManager.play_game_music()` in `_start_first_turn()` so gameplay playlist playback begins reliably after menu/intro flows.

- Famine: `_process_army_food_costs_for_player()` triggers `famine_regions()` when food falls short. For each 1.0 missing food, famine now rolls lookup points `1..10` with weighted odds from `[5, 7, 9, 13, 16, 16, 13, 9, 7, 5]` (middle values most likely), then computes base loss points as `floor(food_deficit * rolled_famine_points)`. After that, losses are applied proportionally across active armies and active garrisons; unit removal remains food-cost-aware (`0.1 food units = 1 point`, horsemen/mounted knights `0.2 = 2 points`). Population/growth are not modified by famine. `GameManager` stores per-player famine summaries (`triggered`, `food_deficit`, `target_points`, `actual_points_removed`, `soldiers_lost`, `by_force`, `by_unit_type`) via `get_latest_famine_result_for_player()` / `consume_latest_famine_result_for_player()`. ### TurnController.gd (TurnController)
- Purpose: Unified turn pipeline for AI (and fits human pipeline shape).
- Flow: frontier discovery → target scoring → build candidates → execute with step-gate → handle battle → continue/recalc.
- Victory integration: aborts AI turn/move loops when `GameManager` reports victory and runs `check_victory_conditions_for_player()` after each completed AI move action.
- Movement: Each AI army picks the best single frontier target to attack; if no valid target exists or merge policy halts on a stronger/unknown enemy, it logs defense and spends the turn camping.
- Frontier fallback: when no hard targets are reachable this turn, `MAIN` armies now advance toward the best unreachable hard target (highest score, then lower mp_cost) instead of camping.
- Enemy intel logging: Target lines mark enemies as “known” only when tracked power exists (tracked armies or garrison memory); first-turn unseen enemies remain unknown.
- Recruitment: When no recruit castle is available (or unreachable via friendly-only paths), the army logs the miss and spends the turn camping/defending; recruitment moves route strictly through owned regions (no hostile hops) when heading to a castle or peasant pickup.
- Economy logging: AI log now records castle build/upgrade candidates with scores plus resource gaps and top-up attempts when builds/upgrades are skipped.
- Log ordering: AI turn intro/header is emitted before pre-move economy execution so direct economy logs (trade/bank/top-up) are grouped under the correct player section instead of appearing at the previous player tail.
- Movement debug logging: target candidate dumps now print top 10 scored candidates (instead of top 3) for easier AI target-selection tracing, and each candidate line includes required `mp_cost` before the score component breakdown.
- Movement debug logging now also prints `Rejected candidates` with explicit filter reasons (overmatched, no friendly path, raider thresholds, merge halt, unreachable this turn) so dropped targets are visible in AI logs.
- For `known_overmatched_filter` rejections, logs now print known enemy army `name:power` details (no score), e.g. `enemies: Army II:56, Army I:34`.
- Signals: `turn_started`, `move_prepared`, `move_started`, `battle_started`, `battle_finished`, `region_conquered`, `turn_finished`.
- Uses: `ArmyPathfinder`, `ArmyTargetScorer`, `BudgetManager` (allocate budgets at turn start), `RecruitmentManager` (hire at castles when requested; AI allows instant hire for `just_raised`), `DebugStepGate`.
- AI castle upkeep: TurnController now runs economy in two phases with one `EconomyAIManager` instance: pre-move economy with emergency reserve lock, then post-move castle threat refresh + castle recruitment execution.
- Castle upgrade bank: `EconomyAIManager` deposits 10% of spendable gold at AI turn start (turn 2+) into `Player.ai_castle_upgrade_savings_gold`, hard-locks that gold from non-upgrade spending, and caps the bank at `Stronghold gold cost * 1.25`.
- Castle reserve budgets: threatened-castle reserve requests now use the same base allocation weight as armies (`1.0` per request), and each castle reserve is capped by recruits (`max gold = 10 * recruits`, `max wood = floor(0.5 * recruits)`, `max iron = floor(0.5 * recruits)`), applied in both pre-move and post-move reserve recalculation.
- Threat-first movement tree: each AI army evaluates threatened-castle actions from a fixed pre-move snapshot (`threat_level >= 2`) before recruitment/peasants and before frontier scoring; threat evaluation is grouped per enemy region (`known_total_power` + `has_unknown`) so same-region enemy stacks are treated as one context for direct-attack power checks. Direct-attack retry guard remains per-army/per-target; when turn-lock is hit, local merge retry is skipped for that target and armies already inside the threatened castle hold/camp. Threat transfer donors are finalized deterministically (request recruitment + camp).
- Threat defense order now runs `direct attack -> local same-region merge check -> support merge -> castle garrison sortie -> reposition fallback`; sortie can now trigger for unknown castle threats (without ratio-based garrison pull), still uses known-threat power-ratio gates when intel exists (`>=120%` feasible, pull only up to `<=150%` target ratio), and for multi-threat castles requires same-turn attack+return MP feasibility before committing.
- Army loop first-step: when an army starts a decision cycle inside a castle with `castle_nearby_entities["enemy_army_ids"]` empty and no directly adjacent enemy-owned regions, it absorbs the full local garrison into itself before threat/recruitment/peasants/role logic.
- Wounded-heal pre-scoring check: after threat/castle-hold/recruitment/peasants steps and before role scoring, armies run `_check_if_heal_wounded()`; if wounded ratio (`wounded / (active + wounded)`) meets difficulty threshold (Easy 50%, Normal 35%, Hard 20%) and MP remains, they repeatedly camp to heal until ratio drops below threshold or MP reaches zero.
- Threat power refresh: threat attack/support/defense checks refresh each threat entry with live tracked enemy power during movement, so known-power comparisons use up-to-date memory instead of stale pre-move snapshot values.
- Two-mode role routing: after threat/recruitment checks (peasants-only cycle is temporarily disabled/commented), armies follow a per-turn role assignment. `EXPANSION` mode (no enemy frontier) sets all armies to `RAIDER`; `WAR` mode uses a hard-target staircase to assign `MAIN`, computes `RAIDER` slots from total frontier size with cap `ceil((hard+soft)/4)`, and marks leftovers as `SUPPORT`. If no `MAIN` is assigned, remaining armies stay `RAIDER` (no support conversion). Targeting uses two buckets: `hard` (enemy region with army or castle) and `soft` (no army/castle, neutral or enemy-owned). `MAIN` prioritizes hard→soft, while `RAIDER` uses one combined scored pool (soft + hard) and applies hard-target exceptions only (known weaker army by 20% or known castle defense by 2x). `SUPPORT` merges to nearest reachable main, else routes to recruitment, else camps.
- Raider unknown-hard gate: for hard targets with unknown enemy strength, raiders no longer always reject; they roll a difficulty-scaled attack chance (Easy 25%, Normal 50%, Hard 75%) before continuing normal merge/attack flow.
- Main hard-target reachability: `MAIN` prioritizes reachable hard targets first; if none are reachable this turn, it can still advance toward the best unreachable hard target instead of immediately falling back to soft targets.
- Live frontier refresh: role behavior refreshes frontier buckets before each army decision pass, so newly conquered regions immediately affect hard/soft target pools within the same turn (roles remain turn-assigned).
- Role move safety: even though role buckets are turn-scoped, target selection revalidates live ownership/bucket state and skips the army’s current region so captured regions cannot be repeatedly selected with zero-cost self-moves.
- Threat defend de-dup: castle fallback reposition now runs a live sufficiency gate so armies do not pile onto the same castle. Unknown threats allow only one defender unless none is present; known threats allow additional defenders only while known threat power exceeds current full castle defense (`armies + garrison + recruits`), and reposition is reach-this-turn only.
- Unknown-threat castle hold/reposition now uses a minimum defense floor derived from the same minimal recruitment-threshold formula (`base_roll=10`, turn-scaled, peasant-power based): level-3 unknown holds are released when current castle defense meets the floor; otherwise the defender stays and castle recruitment can continue.
- Wealth tracking: caches start-of-turn resources for AI log headers, writes the final totals after movement, and calls `PlayerManagerNode.update_player_wealth_status()` so every player ends their turn tagged as poor/normal/rich (thresholds in `GameParameters`).
- Battle Logs: After `_log_army_move_result()` records `"Fight at ..."` lines, `_log_recent_battle_details()` pulls the queued summary from `GameManager.consume_ai_battle_log_for_army()` so AI logs show `Battle started`, attacker/defender stats, the result string (`Won/Defeated/Withdrew`), and the post-battle status lines right after the arrival entry; battle log tokens are captured before travel so freed armies can still retrieve their queued entries, and the header uses the actual contested region returned by `ai_travel_to`.
- Recruitment Loop: Recruitment movement uses a state machine per army (`NORMAL`, `TRANSFER_TO_CLOSEST`, `RECRUIT_OR_DEFEND`) with route resolution per decision pass: it logs `Reachable recruitment castle candidates` first (friendly-only multi-turn paths), then `Breakthrough recruitment castle candidates` (non-friendly paths filtered by bounded clean-breakthrough rules: max 120 explored nodes, max 3 non-friendly regions, and no armies/castles on intermediate non-friendly regions). Fallback transfer/camp runs only when both lists are empty (or breakthrough is blocked by below-half threshold). `RECRUIT_OR_DEFEND` no longer recurses back into `NORMAL` in the same pass, preventing duplicate castle-pick loops. After a successful recruitment-transfer merge, the donor army spends remaining MP on camp to prevent same-turn local-transfer loops.
- Withdrawal Logging: `battle_withdrawal` results note which side withdrew; defender withdrawals are treated as holding the target (no extra movement log), while attacker withdrawals log the retreat destination.
- Post-withdrawal reposition: when an AI army withdraws or loses and still has movement points, it moves to the strongest reachable friendly region within range.
- Calls back into `GameManager.ai_travel_to()` for step-wise movement and battle triggers.
- Reinforcement routing: Armies that need recruitment but have no assigned budget now queue a `goal: reinforce` move toward the best owned castle before chasing frontier targets, so low-power stacks travel home for resupply.
- Castle targeting: When enemy strength is known and the target has a castle, `_build_enemy_info()` triggers `GameManager.simulate_siege_battle()` and `_evaluate_merge_policy()` halts attacks predicted to lose (or withdraw) and proceeds when the sim reports victory.
- Army loop (AI only): per-turn armies are shuffled, then each army loops until MPs are gone — threatened-castle handling, castle-hold, recruitment, peasant recruitment, then role-driven action (`MAIN`/`RAIDER`/`SUPPORT`). If no valid role action remains, the army camps out remaining MP. The loop now hard-stops stage evaluation as soon as MP reaches 0 in-pass, preventing extra scoring/target selection after exhaustion.
- Resting Logic (AI): armies rest to 100% vigor before any move if efficiency < 90% (camp until full or MPs run out), and any time no move is possible they burn remaining MPs camping; end-of-turn pass still exhausts leftover MPs with `make_camp()`.
- Peasants-Only Recruitment:
  - Runs only when standard recruitment is not needed, the player has positive net food growth, and the army is below its wealth-adjusted peasant floor (Poor uses the base 20% minimum, Normal halves to 10%, Rich players skip peasants entirely).
  - Targets peasant share based on army power thresholds, scaled by wealth (Poor uses 40%/30%/20%, Normal halves those shares, Rich uses 0%).
  - Filters candidate regions to those with enough recruits to meet the calculated need, then picks the best recruits-per-(distance+1) ratio so nearby pools are favored.
  - If no region can meet the minimum, the army flags for normal castle recruitment; otherwise it moves/hire peasants for free using standard pathfinding within current MPs.
- AI Logging: During AI turns `TurnController` calls `AILogManager` to write the requested log format — each turn header includes resources, signals, decision, and owned regions, while every army action logs as `Recruits`, `Goes to Castle`, or `Moves` with its target plus recruitment/economy success or failure reasons.
- AI intro logging now prints the current player castle-garrison list immediately before `______ ECONOMY ______` using army-style power/composition lines, e.g. `Keep Northvik [Power: 168 - P:29, S:13, A:7, SW:7, H:1, K:1]`.
- Decision-tree logging: movement decisions emit explicit branch logs for threat handling and role routing (including mode/role selection, raider hard-target exceptions, and support merge/recruit/camp outcomes) via `AILogManager.log_army_decision_tree(...)`.
- AI log entries now show efficiency inline (`Power: 67, E: 95 - P:...`) so it’s easy to see when armies act below full effectiveness.
- Frontier targeting now logs the top 3 scored candidates (name/id, score, resources/pop/level/castle/pursue/strategy components) before selecting the best attack target.

### EconomyAIManager.gd
- Purpose: Central, deterministic AI economy planner with event-driven castle-threat reserve cache.
- Key Turn APIs:
  - `run_pre_move_economy_with_reserve_lock(player_id, turn_number)`: computes signals, analyzes castle threats from `castle_nearby_entities`, builds one shared pre-move recruitment pool for armies + threatened castles, syncs castle reserve lock from that pool, executes early surplus-selling, deposits AI castle-upgrade savings bank (turn>1), evaluates castle upgrades, then runs remaining pre-move economy actions.
  - `run_post_move_castle_recruitment(player_id, turn_number)`: refreshes castle threats after movement, resimulates known threats when needed (unknown->known or power change >15%), recalculates weighted reserve budgets, and executes castle recruitment.
  - `analyze_castle_threats_pre_move(player_id)`: public pre-move threat scan hook.
  - `get_castle_threat_snapshot(player_id)`: read-only deep-copy snapshot for movement decisioning (`threat_levels_by_region`, `threat_registry_by_region`).
- Threat model:
  - Per-castle threat registry keyed by `army_<id>` with `known/power/region_id/threat`.
  - Threat classes: `castle_safe` (known attacker cannot beat castle-alone), `needs_army` (known attacker beats castle-alone but loses vs full defenders), `unknown` (unknown power), `big` (known attacker beats full defenders).
  - Values: `castle_safe=+1`, `needs_army=+2`, `unknown=+2`, `big=+4`; `threat_level` stores max severity `0..4`.
  - Reachability filter: enemy IDs from `castle_nearby_entities["enemy_army_ids"]` are treated as threats only if pathfinding confirms they can reach the castle within one turn (`cost <= MOVEMENT_POINTS_PER_TURN`) using `friendly_only=false`.
  - Threat scan visibility: each castle summary logs all nearby enemy cache entries and marks rejections with reason (`not_in_tracking`, `no_path`, `insufficient_mp`) and computed path cost.
  - Known enemy armies in the same region are merged into one simulated attacker and classified with two simulations (`sim_castle_only`, `sim_with_army`) to derive level 1/2/4.
  - Threat logging: pre/post threat summaries include per-threat detail lines under each castle (`id`, source region, `threat` label/level, `intel` known/unknown, tracked power, `sim_castle_only`, `sim_with_army`) for debugging classification.
- Reserve model:
  - Only castles with `threat_level >= 2` receive emergency budgets.
  - Pre-move recruitment uses one shared budget pool across army and castle requests (castle request weight = `total_threat_value`, army weight = 1.0).
  - Reserved resources are synced from castle shares and hard-locked during pre-move economy spending checks.
  - Separate AI-only upgrade-bank gold lock is applied to all non-upgrade spend checks (recruitment/raise/build/ore/food-buy).
  - Separate AI-only raise-reserve gold lock is applied to all non-raise spend checks (recruitment/build/upgrade/ore/food-buy); raise path can consume this reserve.
- Trade ordering: AI trade is split into `sell_surplus` (before castle-upgrade checks) and `buy_food_deficit` (after all other economy actions).
- Castle-upgrade savings bank: from turn 2 onward, AI deposits 10% of spendable gold into persistent per-player `ai_castle_upgrade_savings_gold`, capped to one Keep->Castle gold cost; successful castle upgrades consume bank gold first in accounting logs. If castle upgrade evaluation finds no viable candidates (`no_upgrade_candidates`), the bank is released (set to 0) so gold is no longer locked.
- Raise-army reserve bank: AI accumulates persistent per-player `ai_raise_army_savings_gold` up to `RAISE_ARMY_COST` using partial carry-over (`add = min(cap - current, spendable_gold)`), only when raise intent exists (`candidate` or `armies == 0`) and no severe castle threat (`threat_level < 2`); reserve is consumed by successful raise and released when raise returns `no_candidate`.
- Integration: TurnController now runs this manager in two phases (pre-move + post-move) within one AI turn instance.
- Recruitment budget safety: pre-move economy now clears stale recruitment flags on armies that no longer need reinforcement, re-runs allocation for any still-needing castle army that ended up without `assigned_budget`, and applies a non-null fallback budget object to prevent recruitment wait loops.
- Army recruitment ownership guard: pre-move army recruitment/budget assignment is now restricted to armies standing in player-owned castle regions; no army recruitment is performed from enemy/neutral castles.

- Priority Flow:
  - If any armies at castles need recruitment this turn → allocate recruitment budgets and skip raising/building.
  - Else try to raise an army; if raised → allocate recruitment for the new army and skip region spending.
  - Else defer region economy to post-movement phase.
- Castle building (post-move): checks Outpost affordability, scans owned regions without castles, scores each as `strategic_heatmap*10 + neighbor_support` (friendly neighbors +15, neutral +5, enemy -10, and `-45` if any neighboring region already has a castle). Castle regions themselves are excluded; neighboring-castle regions are penalized (not hard-blocked) so high strategic value can still win. Candidates below 100 points are rejected. A candidate must also be closer to at least one enemy castle than any current friendly castle (BFS distances cached per map). Winning region starts an Outpost build immediately and the action is reported back for AI logging.
- Castle upgrades: evaluates every owned castle not already upgrading. Score = normalized recruit availability (total recruits from the castle plus neighbors) + normalized proximity to enemy castles. The closest/highest-recruit castle gets 100 per axis; others scale proportionally. The best affordable candidate upgrades to the next tier (Keep → Castle, etc.) while logging the full evaluation list.
- Region upgrades: continuously promotes the best non-max-level regions while the player can afford the promotion cost. Score = (castle level ×2) + population/100 + neighboring friendly castle levels + recruit status bonus (empty +2, partial +1, full −2) − current region level. Every successful promotion logs `"Upgrading <region> to <level> (score: X)"`.
- Region upgrades call `PlayerManagerNode.meets_food_upgrade_safeguard()` so the AI skips promotions that would drop projected food (stock − food cost + growth) below `AI_MIN_FOOD_AFTER_UPGRADE`.

#### Raise Army AI (implemented)
- Goal: Prefer fewer, stronger armies over many weak ones; raise only when we have support and coverage gaps.
- Decision flow:
  1. `pick_best_raise_region()`: Find best castle (level ≥ 2) with enough recruits (≥ AI_MIN_RECRUITS_FOR_RAISING)
  2. `should_raise_army()`: Normalized model over 4 factors via `ai/RaiseArmyDecision.gd`, returns decision + formatted score text for logging
  3. `execute_raise_army()`: Create army and deduct cost
- Gates:
  - Recruits: `recruits_total >= AI_MIN_RECRUITS_FOR_RAISING` (skipped for first-army bootstrap when `armies == 0`)
  - Gold reserve: `player.gold - RAISE_ARMY_COST >= AI_RESERVE_GOLD_MIN`
  - Capacity: ignores castles already hosting `GameParameters.MAX_ARMIES_PER_REGION` armies; execution aborts (with gold restored) if a cap race happens mid-action.
- Logging: decline reasons now include concrete gate/threshold values (for example gold reserve after raise, recruits minimum, frontier pressure minimum, or score below threshold) in the `Raise Army:` economy line; `Frontier2Army` score text uses a guarded ratio (`0.0` when army count is zero) to avoid division-by-zero crashes.
- First-army rule: when `armies == 0`, raise decision score returns pass (`1.0`) if the raise cost is affordable, so AI can bootstrap at least one army; reserve/frontier guards are applied once at least one army exists.
- Scoring factors (normalized 0..1):
  - Region/Army ratio within band `[AI_RAISE_R2A_BAND_MIN..MAX]`
  - Average MP distance of armies to candidate castle `[AI_RAISE_DIST_MIN..MAX]`
  - Recruits and Gold (bank) above minimums
  - Raise-candidate selection now also adds `free_garrison_bonus` to candidate score when that castle has no recruitment-requested friendly armies in-region and no nearby enemy army IDs in `castle_nearby_entities`; bonus is scaled as `garrison_power / 4`.
  - Weights:`AI_RAISE_W_R2A`, `AI_RAISE_W_DIST`, `AI_RAISE_W_RECRUITS`, `AI_RAISE_W_BANK`
  - Threshold: `AI_RAISE_THRESHOLD_NORM`
- Execution: One raise per turn max, deterministic tie-break by region_id
- Tuning: GameParameters (`AI_RAISE_*` normalized constants) and `ai/RaiseArmyDecision.gd`

- F8 Screenshot: `GameManager._unhandled_input(KEY_F8)` calls `Utils.take_screenshot()`. It centers and zooms out the camera, hides `UI`, captures the viewport, restores `UI` and camera, and saves to `res://screenshots/screenshot.png`.

- Camera Centering: Auto-centers on armies/assets. `CameraController.await_target_reached()` replaces arbitrary delays; `GameManager.ai_travel_to()` awaits camera arrival instead of timers. For human players: `GameManager._on_current_player_changed()` centers on first army or castle, but skips recentering while any battle is active to prevent mid-battle camera jumps.

## Data & Parameters
- Player.gd: resources, name/color/id, afford/pay helpers, serialization, plus a per-player `wealth_level` flag (poor/normal/rich) that TurnController updates at the end of each turn so recruitment logic can read each player's current tier, persistent AI-only `ai_castle_upgrade_savings_gold` (castle-upgrade funding), persistent AI-only `ai_raise_army_savings_gold` (carry-over raise reserve), and enemy intel memory (`enemy_army_memory` power/rounds, unlimited `enemy_army_composition_memory` with `turns_ago`, and round-limited garrison composition memory) used by InfoModal intel view.
- ResourceComposition.gd / ArmyComposition.gd: storage and math helpers; food cost, power.
- GameParameters.gd: unit stats and costs, recruitment caps and growth, movement costs, mining/search, castle defense, AI weights, pathfinder/AI constants, icons/scales, peasants-only recruitment parameters (AI_PEA_*), camera timing constants (CAMERA_*), configurable prebattle ranged volley count (`PREBATTLE_VOLLEY_ROUNDS`, currently `2`), optional attacker terrain-vigor penalties (`BATTLE_ATTACKER_TERRAIN_VIGOR_PENALTY_ENABLED` + per-terrain penalty map), optional ranged terrain hit reduction for archers/crossbowmen in forest/forest-hills (`BATTLE_RANGED_TERRAIN_PENALTY_*`), and the new wealth thresholds + composition tables used to pick poor/normal/rich army and garrison mixes. Current tuning: region recruit-cap percentages are L1..L5 = `4%/5%/6%/7%/8%`, constant population growth is `0.00`, generated starting garrisons get a `+2` baseline, and selected biome resource rolls use weighted outcomes (grassland food/forest wood/hills stone `1:45%`, `2:35%`, `3:20%`; forest-hills wood `1:65%`, `2:35%`; forest-hills stone `0:45%`, `1:35%`, `2:20%`).
- Enums (Enums/*.gd): Regions, Levels, Soldiers, Players, Resources, Unit traits, Castle types.
- Wealth scaling: GameParameters’ peasant ratios shrink by wealth tier (Normal halves, Rich zeroes) across army/garrison ideal compositions and the AI peasants-only min/target proportions so richer players favor pricier units automatically.

## Static vs Dynamic
- Static nodes: `Map/Regions`, `Map/Ocean`, `Map/Frame`, all UI nodes under `UI`, and `Players/Player1..6` containers.
- Dynamic nodes: `Region` instances under `Map/Regions` (land + ocean; ocean `Polygon` hidden, visuals from `Map/Ocean`), `Army` nodes parented to regions, `Castle` sprites under regions, border/overlay visuals.
- Border widths: `BorderManager` scales internal/ownership Line2D widths and ownership offsets from `MapGenerator.get_map_visual_scale()` (region-count profile).
- Icon scaling: map visual scale now resolves from region-count profile (`Utils.resolve_map_profile`) with anchor counts `tiny=137`, `small=264`, `medium=504`, `large=1040`, `huge=2104` and log interpolation between anchors; mountains still use aspect-ratio fit logic and only apply the shared Y offset scaling.
- RegionIconManager.gd: MapGenerator delegates all biome icon placement here; it randomizes hill/forest/hill_forest variants (`<biome>_1..3.png`), supports both `hill_forest` and `forest_hills` biome naming aliases for the same icon family, offsets standard icons, and picks the mountain sprite with the nearest proportions before fitting it inside the region; internal-mountain detection from `MapGenerator` is kept for potential scaling adjustments but currently applies a neutral 1.0 multiplier.
- Starting armies use `GameParameters.STARTING_ARMY_COMPOSITION_HUMAN`/`_AI` selected through `GameManager.get_starting_army_composition_for_player()` and passed into `Army.setup_army()`.
- Border widths and offsets: all runtime consumers (biome icons, castles, armies, movement arrows, and ownership borders) use the same region-count visual scale source from `MapGenerator`.
- Center markers: `MapGenerator.set_center_markers_enabled(true)` adds a `CenterMarkers` Node2D full of small red Polygon2D squares at each non-ocean region center (used by the GameManager debug toggle).
- Polygon centroids: Every time MapGenerator loads JSON or BorderManager rebuilds noisy polygons it recomputes the centroid for each region polygon (shoelace method with degenerate average fallback), stores it back into `region_by_id`, pushes it into `Region.center`, and writes it to each Polygon2D’s `center` metadata so castles/armies/icons/debug dots always anchor to the real geometric center instead of stale JSON values.
- Mountain adjacency: BorderManager skips drawing internal borders when both touching regions are mountains so mountain ranges remain uninterrupted visual blobs.
- Mountain icon layering: After every icon pass MapGenerator reorders all mountain sprites (marked via `mountain_icon` metadata) by their region center Y and assigns strictly increasing z-indexes so upper mountains render behind lower ones.

## Notable Relationships
- GameManager wires all managers, creates `TurnController`, and hands references around; UI/battle events flow back through `BattleManager` → `GameManager.finalize_battle_result`.
- Sound: `SoundManager` respects `music_enabled`; `GameManager` does not force-enable music. Retreat horn (`sounds/retreat_horn.mp3`) plays via `SoundManager.play_retreat_horn()` whenever BattleModal shows a withdrawal message. Battle sound (`sounds/battle.wav`) plays at 50% volume through `SoundManager.play_battle_sound()` when BattleModal opens, starts from a random position in the first half of the clip, and loops until stopped/faded.
- Sound players run with `PROCESS_MODE_ALWAYS` so opening the in-game menu (tree pause) does not stop music/SFX.
- Music playlists: `SoundManager` hosts `Playlist` (tracks + shuffle + repeat) and predefined `PLAYLIST_DEFS` with a tutorial playlist (`track2.mp3`, then `track1.mp3`, no shuffle, repeats) and a custom-map playlist (`track1.mp3`–`track7.mp3`, shuffle on, repeat). `GameManager` activates the tutorial playlist when tutorial mode is enabled and the custom-map playlist whenever game mode is custom; the music player advances through the playlist on the `AudioStreamPlayer.finished` signal, looping from the start.
- Wounded: Simple wounded system added. `GameParameters.WOUNDED_CHANCE` base chance; per casualty wounded chance is `base * (1 + defense%)`. `Utils.compute_wounded()` calculates wounded per unit type from loss dicts. Wounded are computed exactly once when a battle finishes (modal path computes on finish; background path sets it before finalization). `GameManager.finalize_battle_result()` never computes wounded; it assumes they exist on the report, allocates them proportionally (attackers: attacker army; defenders: across defending armies, garrison, and recruits), then applies losses. `Army` tracks a separate `wounded_composition` excluded from battles and excluded from food upkeep.
  - Storage: `Army.wounded_composition`, `Region.wounded_garrison`, `Region.wounded_recruits` (peasants only).
  - Allocation: Wounded distributed proportionally by availability before losses are applied. Defenders include armies, garrison, and recruits in the proportional distribution.
  - Summary: Battle summary displays total wounded from all sources; loss application removes from active comps/recruits.
- Healing: `GameParameters.CAMP_HEAL_CHANCE` controls healing probability. `Army.make_camp()` calls `heal_army(false)` to attempt healing across all wounded (per-unit chance). `Army.heal_army(force_at_least_one=false)` heals each wounded unit independently by chance; if `force_at_least_one` it guarantees at least one heal when wounded remain. There is no free post-battle heal on defeat or withdrawal; healing occurs only when making camp.
 - Healing: `GameParameters.CAMP_HEAL_CHANCE` controls army healing when camping. There is no free post-battle heal on defeat/withdrawal. At the start of a player's turn, all owned regions fully heal their regional wounded pools: `RegionManager.heal_wounded_for_player(player_id)` moves `Region.wounded_garrison` back into `garrison` and clears `Region.wounded_recruits` (peasants). This is invoked in `GameManager._process_player_turn_start()` before income.
- Ownership Overlays: Creation/update centralized in `MapGenerator`. Every non-ocean region always carries an `OwnershipOverlay`; neutral ownership keeps it fully transparent rather than removing it so highlight/tween logic can reuse it (existing tinted overlays are preserved).
  - `create_ownership_overlay(region_id, player_id)`: Ensures the overlay exists, syncs the noisy polygon, and applies the player tint (alpha 0.4).
  - `update_ownership_overlay(region_id, player_id)`: Recolors existing `OwnershipOverlay` without changing alpha; used when conquering non‑neutral regions.
  - `remove_ownership_overlay(region_id)`: Resets overlay color to transparent neutral black (keeps node alive for reuse).
  - `RegionManager.set_region_ownership` still calls create for previous owner = -1, update otherwise; neutralizing a region routes through `remove_ownership_overlay`.
 - InfoModal: Region view shows garrison totals/recruits plus garrison composition under Defenders; costs hide when the resource cost is 0.
 - InfoModal intel rendering is per-army card: only enemy/non-selectable armies are masked with `?`, while player-owned armies keep full stats even in neutral/enemy regions (used by SpawnEvent manual placement flow).
- TurnController owns pathfinder/scorer; calls `GameManager.ai_travel_to` for movement and battle stepping; uses `BudgetManager` and `RecruitmentManager` when armies request reinforcement.
- PlayerManagerNode is the authoritative per-player economy and emits player-change signals used by UI.
 - AI camera pacing: `GameManager` routes AI actions (castle placement, move steps, battle resolution) through `AICameraDirector` to enforce pre-action and post-action waits; camera snaps instantly to targets and all AI camera delays scale down with the AI Speed modal when set above Normal.

### army_manager.gd (ArmyManager)
- Purpose: Army creation, selection, and adjacent-region movement.
- Key: `create_army()`, `move_army()`, `move_army_to_region()`, `reset_all_army_movement_points()`.
- SpawnEvent support: `show_custom_target_arrows(target_ids, source_region_by_target)` and `clear_custom_target_arrows()` render the same arrow/highlight style for explicit (non-neighbor) placement targets.
- Capacity: `GameParameters.MAX_ARMIES_PER_REGION = 5` enforced on creation/movement helpers (`is_region_at_army_cap`, `get_armies_in_region`, `get_army_count_in_region`) so UI/AI respect the stack limit.
- Stacking: `_apply_army_offsets_for_region(region)` repositions all armies in a region to avoid overlap using fixed extra offsets. Applied on create, move (both source and target), and retreat. Pattern: 1st = base; 2nd = x-15/y-10/z-1; 3rd = x-30/y-20/z-2; 4th = x+15/y-10/z-3; 5th = x+30/y-20/z-4; 6th+ same as 1st.
- Ready highlight: Caches `_ready_highlight_player_id`, listens to `Army.movement_points_changed`, and refreshes `VisualManager.update_ready_army_highlights()` on turn start, move/camp MP spend, resets, and army removal.
- Retreat Support: `get_previous_region_for_army()` exposes the last region so cameras can focus on withdrawal destinations.
- Raised armies now spawn with 1 peasant token (set in `Army.setup_raised_army`) to avoid empty stacks on creation.
- Selection: `move_army()` preserves the active selection when the moved army was already selected (so the selected region updates to the new location after movement).
- Nearby cache events: exposes cache maintenance hooks (`on_army_created`, `on_army_moved`, `on_army_removed`, `on_region_castle_presence_changed`, `on_region_owner_changed`) and `debug_log_nearby_entities_for_region(region_id)` used by Ctrl-hover debug dumps.
- Fast entity lookup: `get_army_by_entity_id()` / `get_army_by_instance_id()` resolve armies via the central `army_by_entity_id` index, avoiding repeated full scans in AI turn logic.

### ai_camera_director.gd (AICameraDirector)
- Purpose: Coordinates AI camera focus and timing around the shared `CameraController`.
- Key: `await_focus_on_army()`, `await_focus_on_region()`, `await_delay()`.
- `GameManager` uses it to wrap AI castle placement, movement steps, and battle resolution with the configured pre/post waits.
